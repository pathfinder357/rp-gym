# 부하 실험 — 동기화 정각 스파이크 (2026-09-28 설계 합의)

작성 2026-09-27 · 실행 환경 EC2 라이브 서버 · 주입 도구 JMeter

## 1. 질문

Health는 30분마다 동기화한다. 전 유저가 정각에 몰리면 `HEALTH_ACTIVITY_SYNCED`가 N건 한꺼번에 `health.events`에 들어온다.

> **정각에 들어온 N건을 다음 주기(1,800초) 전에 다 소화하는가? 소화하지 못하는 N은 얼마부터인가?**

1,800초를 넘기면 다음 정각분이 밀린 위에 또 쌓이고, lag이 줄지 않고 계속 늘어난다.

## 2. 왜 HTTP가 아니라 Kafka로 주입하나

이 서비스의 트래픽은 API 호출이 아니라 이벤트로 들어온다. Health 동기화 API를 때리면 Health 쪽 병목이 먼저 걸린다. 당일 첫 동기화에 AI 호출이 트랜잭션 안에 있고, 실측 응답이 4~16초다. 그러면 내 컨슈머는 측정되지 않는다.

그래서 JMeter가 `health.events`에 직접 발행한다. 이벤트 형식은 Health 프로듀서와 똑같이 맞추고, 키는 userId다.

HTTP 응답 시간이 빨라도 처리가 빠르다는 뜻은 아니다. 비동기 구조에서 처리량은 **컨슈머가 lag을 소진하는 속도**로 정의한다.

## 3. 측정 지표

| 지표 | 얻는 방법 | 뜻 |
|---|---|---|
| 소진 시간 | 발행 시작부터 마지막 스냅샷 저장까지 (DB). 시작 전과 끝난 뒤에 lag 0 확인 | 합격 기준(1,800초)과 직접 비교 |
| 처리량 (건/초) | N / 소진 시간, 그리고 초별 처리 건수 | 병목이 걸리는 지점 |
| 처리 지연 p50 / p95 / max | `user_latest_snapshots.updated_at − measured_at` | 정각에 동기화한 유저가 판정까지 기다리는 시간 |
| 최대 lag | 샘플 중 최댓값 | 피크 크기 |

`measured_at`은 주입한 이벤트의 측정 시각, 곧 정각이다. `updated_at`은 스냅샷이 저장된 시각이다(JPA Auditing, UTC). 그래서 둘의 차이는 **정각부터 내 컨슈머가 그 유저를 처리할 때까지의 지연**이다. 코드를 고치지 않고 DB만으로 얻는다.

## 4. 시나리오 — 경로의 양 끝을 잰다

동기화 한 건마다 트랜잭션 2개가 순서대로 열린다(개인 퀘스트 → 파티 퀘스트). 경로 길이는 유저 상태에 따라 달라진다.

| 시나리오 | 시드 | 타는 경로 | 의미 |
|---|---|---|---|
| S0 가벼운 끝 | 유저만, 퀘스트 없음 | 스냅샷 조회·저장 → 퀘스트 없음 → 파티 퀘스트 없음 | 하한. 모든 이벤트가 반드시 치르는 비용 |
| S2 무거운 끝 | 전원 활성 개인 퀘스트 + 4인 파티 퀘스트 참여, 이번 이벤트로 진행만 함 | 위 + 퀘스트 판정·UPDATE + 멤버 행·공유 카운터 UPDATE + 완료 선점 시도 | 상한. 파티 공유 행 경합 포함 |

실제 비율은 양 끝 사이에 있다. 활성 퀘스트 보유율 같은 현실 비율은 근거를 댈 데이터가 없어서 임의로 정하지 않는다. 대신 양 끝을 재서 "어느 비율이든 이 범위 안"이라고 말할 수 있게 한다.

완료는 유저당 하루 1회 수준이라 정각 스파이크의 대부분은 진행 갱신이다. 완료 경로(XP·outbox)는 S2 결과를 본 뒤 필요하면 따로 잰다.

## 5. N을 늘리는 순서 (한계 찾기)

```
N = 1,000 → 5,000 → 10,000 → 50,000
```

각 N에서 소진 시간이 1,800초 안이면 다음 N으로 넘어간다. 처리량이 N과 무관하게 일정하면 1,800 × 처리량이 곧 한계 N이다. 이것도 계산값이 아니라 실측으로 확인한다.

## 6. 한 번 실행의 절차

```
0. 사전 점검   서버 소음 확인 — 실험 외 이벤트가 들어오는지 (Health synthetic 스케줄러)
               컨슈머 그룹 game-service lag 0 확인
1. 정리·시드   99_cleanup.sql → 01_seed_S0.sql 또는 01_seed_S2.sql
2. 워밍업      다른 유저 500건 주입 → lag 0 대기   (JIT·커넥션 풀 콜드 스타트 제거)
3. 주입        JMeter — N건을 한꺼번에, 같은 measuredAt. 발행 시작·끝 시각을 파일로 남김
4. 관측        2초마다 처리된 행 수(DB) → progress.csv, 5초마다 docker stats → stats.csv
5. 결과 SQL    03_result.sql — 처리 건수 = N 확인, 소진 시간, 초당 처리량, 지연 p50/p95/p99
6. 환경 기록   코어·메모리, 파티션, 컨슈머 멤버, game 컨테이너 기동 시각

전부 run_spike.sh 한 번으로 돈다:  ./run_spike.sh <라벨> <시나리오> <N>
```

2번이 0.6초 의문을 푼다. 워밍업 전후의 건당 시간을 비교하면 콜드 스타트였는지 알 수 있다.

### 측정 도구가 측정을 오염시키지 않게

서버는 2 vCPU · 메모리 7.6GB(여유 2.2GB) · 스왑 없음이고, 컨테이너 19개가 떠 있다.

- lag을 매초 재지 않는다. `kafka-consumer-groups.sh`는 호출마다 JVM을 띄우므로 2코어에서 매초 부르면 컨슈머와 CPU를 다툰다. 진행 중 관측은 DB 카운트(인덱스 범위 조회)로 하고, lag은 시작 전·끝난 뒤에만 본다
- JMeter 컨테이너는 CPU 0.5코어 · 메모리 768MB · 힙 512MB로 묶는다. 스왑이 없어서 메모리를 넘기면 다른 컨테이너가 OOM으로 죽을 수 있다
- 발행은 스레드 1개가 비동기로 보내고 끝에 flush로 한꺼번에 확인한다(acks=all). 발행에 걸린 시간을 따로 기록해서 소진 시간과 분리한다

## 7. JMeter를 어디서 돌리나 — (a)로 결정

운영 compose의 Kafka는 `INTERNAL://kafka:9092`만 열려 있다. 외부 리스너가 없어서 서버 밖의 JMeter는 붙을 수 없다. SSH 터널도 안 된다. 브로커가 `kafka:9092`로 광고하므로 클라이언트가 그 주소로 다시 접속한다.

| 방법 | 대가 |
|---|---|
| (a) EC2 안, 같은 docker 네트워크의 JMeter 컨테이너, CPU 제한 ← 제안 | 주입하는 몇 초 동안 CPU를 나눠 쓴다. 측정 대상이 주입 이후의 소진 시간이라 영향이 작고, `--cpus`로 상한을 건다 |
| (b) Kafka에 외부 리스너 추가 + 보안그룹 개방 | 운영 compose 변경이라 팀 합의가 필요하고, 브로커를 외부에 노출한다 |
| (c) 같은 VPC에 JMeter용 EC2 추가 | 가장 깨끗하지만 (b)의 리스너 변경이 여전히 필요하다 |

(a)를 고르면 주입 중 JMeter 컨테이너의 CPU 사용량도 함께 기록해서, 측정 오염이 얼마였는지 수치로 남긴다.

## 11. 분해 (S2-N20000-bd, 2026-09-28) — 병목은 커밋 시 WAL 동기화

### A. 이벤트 1건당 DB 작업 (통계 증감 / 20,000)

| 항목 | 건당 | 뜻 |
|---|---|---|
| 커밋 | **2.07** | 트랜잭션 2개 (개인 T1 · 파티 T2) |
| 인덱스 조회 | 약 10 | 스냅샷 2 · 퀘스트 2 · 파티 퀘스트 3 · 파티 멤버 3 |
| UPDATE | 4.0 | 스냅샷 · 퀘스트 · 멤버 · 파티 카운터 각 1 |
| 디스크 읽기 | 0.00 | 전부 메모리. 조회는 병목이 아니다 |

### B. 리스너 스레드가 기다린 것 (덤프 18회 × 3스레드)

| 상태 | 비율 |
|---|---|
| DB 쿼리 응답 대기 | 42.6% |
| **DB 커밋 대기** | **29.6%** |
| 애플리케이션 코드 | 16.7% |
| Kafka 오프셋 커밋 | 7.4% |

리스너 #0(다른 컨슈머 그룹)은 100% 대기 — 이 부하와 무관.

### C. DB 세션이 기다린 것

| 대기 | 비율 |
|---|---|
| **WALSync + WALWrite (커밋 시 디스크 동기화)** | **58.5%** |
| idle in transaction (앱의 다음 명령 대기 = JPA 왕복) | 34.1% |
| 행 잠금(Lock) | **0%** — 파티 공유 행 경합은 병목이 아니다 |

### 해석

- 커밋할 때마다 PostgreSQL 이 WAL 을 디스크(EBS)에 fsync 하고, 그 동안 스레드가 기다린다
- S0 는 파티 트랜잭션이 조회만 하고 끝나 WAL 을 쓰지 않는다 → **디스크 동기화 커밋 1회 / 건 → 3.7ms**
- S2 는 두 트랜잭션 모두 UPDATE 가 있다 → **디스크 동기화 커밋 2회 / 건 → 7.1ms**
- 건당 시간이 "디스크 동기화 커밋 횟수"에 거의 비례한다. CPU 가 남는 것과도 맞는다
