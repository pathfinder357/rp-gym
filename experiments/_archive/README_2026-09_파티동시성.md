# 동시성 실험 — 파티 100개 × 멤버 4명 = 이벤트 400건

> 이 프로젝트에서 **"돈이 오가는 상황에서 동시성이 정확한가" 를 증명하는 유일한 장치**다.
> 재고 한정 보상이 범위에서 빠지면서 이것 하나만 남았다.

## 이 실험이 증명하는 것

네 명이 동시에 마지막 기여를 넣어 목표에 닿을 때,

```
완료가 정확히 한 번 일어나고,  XP 가 멤버당 정확히 한 건만 나간다
```

잘못 짜면 둘 중 하나가 터진다.

| | 증상 | 원인 |
|---|---|---|
| 중복 지급 | XP 가 1600건 (400의 네 배) | 상태를 읽어서 애플리케이션이 판단하고 조건 없이 UPDATE 했다 |
| 완료 누락 | 완료가 100건보다 적다 | 멤버 기여분을 그때그때 합산했다. 커밋 전인 남의 기여가 안 보인다 |

## 숫자를 이렇게 잡은 이유

```
멤버 기준값 1000,  이벤트 누적값 2000  →  한 사람의 기여가 정확히 1000
파티 목표 4000                        →  네 명이 전부 반영돼야 도달
```

**한 명이라도 빠지면 완료되지 않는다.** 네 번째가 커밋되는 순간에만 완료가 가능해서,
완료 선점에 가장 강한 경쟁이 걸린다.

---

## 0. 먼저 — 설정 하나가 없으면 이 실험은 아무것도 증명하지 못한다

`spring.kafka.listener.concurrency` 가 없으면 기본값이 **1** 이다.
컨슈머 스레드 하나가 파티션 전부를 순서대로 처리하므로,
400건을 한꺼번에 쏟아부어도 **완료 선점이 한 번도 경쟁하지 않는다.**

실험은 통과한다. 그런데 통과가 아무 의미도 없다.

```yaml
spring:
  kafka:
    listener:
      concurrency: 3        # 2026-09-21 추가. 토픽 파티션 수와 맞춘다
```

파티션 하나는 여전히 스레드 하나에만 배정되므로
**"같은 유저의 이벤트는 순서대로 처리된다" 는 성질은 그대로 유지된다.**

> 이 사실 자체가 실험의 절반이다. 7절의 대조군에서 다시 쓴다.

## 1. 준비

### 머지로 달라진 것 세 가지 (2026-09-22)

파티 PR 이 develop 에 머지되어 **V5 · V6 이 들어왔다.** V1 부터 V7 까지 번호가 빈 곳 없이
이어지므로 예전에 걱정하던 순서 문제가 사라졌다. 대신 세 가지가 새로 생겼다.

**하나. 파티 배치가 함께 돈다.**
`PartyScheduler` 가 10 초 · 60 초 주기로 모집 마감과 파티 종료를 처리한다.
시드가 넣는 파티는 이미 `ACTIVE` 이고 `ends_at` 이 6 일 뒤라 배치가 건드리지 않는다.
다만 로그에 파티 배치 줄이 섞이므로, 7 절에서 스레드를 셀 때 반드시
`파티 퀘스트 완료` 로 정확히 걸러야 한다.

**둘. 알림 서비스로 나가는 HTTP 가 생겼다.**
파티 쪽이 알림 5 종을 Feign 으로 직접 보낸다. 알림 서비스가 안 떠 있으면 그 호출이 실패한다.
이 실험은 파티 이벤트를 만들지 않으므로(시드가 직접 INSERT 한다) 영향이 없다.
로그에 Feign 실패가 보이면 이 실험과 무관한 것이다.

**셋. V7 의 물리 FK 가 이제 실제로 걸린다.**
`party_quests.party_id` → `parties.id` 다. 시드가 파티를 먼저 넣으므로 순서는 맞다.

### 스키마를 0 부터 올린다

실험 전후를 깨끗하게 비교할 수 있고, **V7 이 처음으로 V5 · V6 뒤에서 도는 것**을
이번에 함께 확인하게 된다.

```sql
-- 내 로컬 game_db 에서만
DROP SCHEMA IF EXISTS game_service CASCADE;
```

`flyway_schema_history` 도 이 스키마 안에 있으므로 함께 사라진다.

### 기동

```bash
docker compose -f docker-compose-develop.yml up -d postgres-game kafka redis
gradlew.bat :game-service:bootRun
```

**기동 성공 자체가 검증 하나다.** `ddl-auto: validate` 라서 V5 · V6 · V7 이 만든 테이블과
엔티티가 한 칸이라도 어긋나면 기동이 실패한다.

```sql
SELECT version, success FROM game_service.flyway_schema_history ORDER BY installed_rank;
-- V1 부터 V7 까지 전부 success = true
```

로그를 파일로 남긴다. 7절에서 스레드 수를 세야 한다.

```powershell
.\gradlew.bat :game-service:bootRun 2>&1 | Tee-Object -FilePath boot.log
```

> **이 파일은 UTF-16 으로 저장된다. 막을 수 없다.**
> Windows PowerShell 5.1 의 `Tee-Object` 에는 `-Encoding` 매개변수가 아예 없다(6.0 에서 추가됐다).
> 그래서 **읽는 쪽에서 맞춘다 — `Select-String` 에 반드시 `-Encoding unicode` 를 준다.**
> 빠뜨리면 어떤 패턴을 넣어도 0건이 나온다.

기동되면 데이터를 넣는다.

PowerShell 은 `<` 입력 리디렉션을 지원하지 않는다. 파일을 컨테이너로 복사해서 `-f` 로 읽힌다.
한글이 들어 있어 파이프로 넘기면 인코딩이 깨질 수 있는데, 복사는 바이트를 그대로 옮긴다.

```powershell
docker cp 01_seed.sql rp-gym-postgres-game:/tmp/01_seed.sql
docker exec rp-gym-postgres-game psql -U postgres -d game_db -f /tmp/01_seed.sql
```

마지막 줄이 `100 / 100 / 400 / 400` 이어야 한다.

## 2. 이벤트 파일 만들기

템플릿에 시각 두 개를 채운다. **지금 시각이어야 한다** — 시드의 측정 시각(한 시간 전)보다 뒤,
파티 퀘스트 기한(여섯 시간 뒤)보다 앞이어야 한다.

```powershell
$measuredAt = [DateTimeOffset]::Now.ToString("yyyy-MM-ddTHH:mm:sszzz")
$date       = [DateTime]::Now.ToString("yyyy-MM-dd")

(Get-Content 02_events.template.txt -Encoding UTF8) `
    -replace '__MEASURED_AT__', $measuredAt `
    -replace '__DATE__', $date |
    Set-Content 02_events.txt -Encoding UTF8
```

한 줄 확인.

```powershell
Get-Content 02_events.txt -TotalCount 1
```

`__` 가 남아 있으면 치환이 안 된 것이다.

## 3. 400건 발행

파일을 컨테이너에 복사하고, 리디렉션은 컨테이너 안의 셸이 하게 한다.
PowerShell 에서는 `<` 를 쓸 수 없으므로 `sh -c` 안으로 넣는 것이 중요하다.

```powershell
docker cp 02_events.txt rp-gym-kafka:/tmp/events.txt

docker exec rp-gym-kafka sh -c "/opt/kafka/bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic health.events --property parse.key=true --property key.separator='|' < /tmp/events.txt"
```

**키를 주는 것이 필수다.** 키가 없으면 같은 파티의 네 멤버가 어느 파티션으로 갈지
알 수 없고, 무엇보다 같은 유저의 이벤트 순서가 깨진다.

파일은 같은 파티의 네 명이 이어지도록 정렬돼 있다. 연달아 발행되므로 거의 동시에 소비된다.

## 7. 동시성이 진짜였는지 — 이걸 안 보면 실험이 반쪽이다

전부 통과해도 **직렬로 처리됐다면 증명한 것이 없다.** 경쟁이 실제로 있었는지 확인한다.

> **`-Encoding unicode` 를 반드시 붙인다.** 로그가 UTF-16 이라 없으면 0건이다.
>
> **검색어는 한글이 아니라 클래스명으로 잡는다.**
> 로그 파일 안의 한글은 콘솔 코드페이지를 거치면서 깨져 있다.
> `파티 퀘스트 완료` 는 파일 안에 그런 글자로 존재하지 않으므로 절대 안 맞는다.
> 완료 로그를 유일하게 식별하는 것은 `PartyQuestProgressService` 와 `rewardXp=` 다.

### 완료 로그가 정확히 100줄

```powershell
(Select-String -Path boot.log -Pattern "PartyQuestProgressService.*rewardXp=" -Encoding unicode).Count
```

100이어야 한다. 이 숫자가 100인데 원장이 400이라는 것이
**"완료 판정은 한 번, 지급은 네 명" 이 정확히 일어났다**는 뜻이다.

### 처리에 참여한 스레드 수

로그 한 줄의 대괄호는 셋이다 — `[game-service]` `[스레드이름]` `[traceId,spanId,eventId]`.
스레드는 **두 번째**이므로 분해했을 때 인덱스 `[3]` 이다.

```powershell
Select-String -Path boot.log -Pattern "PartyQuestProgressService.*rewardXp=" -Encoding unicode |
    ForEach-Object { ($_.Line -split '\[|\]')[3].Trim() } |
    Group-Object | Format-Table Count, Name
```

**두 개 이상**이어야 한다. 하나면 직렬 처리였다는 뜻이다.

### 같은 파티의 네 명이 서로 다른 스레드로 갈라졌는가 — 가장 강한 증거

스레드가 여러 개인 것만으로는 부족하다. **같은 파티 퀘스트 행을 서로 다른 스레드가
동시에 건드렸어야** 완료 선점이 실제로 경쟁한 것이다.
MDC 의 eventId `55555555-0000-4000-8000-{파티9자리}{멤버3자리}` 로 묶어서 센다.

```powershell
Select-String -Path boot.log -Pattern "result=Applied" -Encoding unicode |
    ForEach-Object {
        $t = [regex]::Match($_.Line, 'ntainer#0-(\d)-C-1').Groups[1].Value
        $p = [regex]::Match($_.Line, '55555555-0000-4000-8000-(\d{9})\d{3}').Groups[1].Value
        if ($t -and $p) { "$p $t" }
    } | Sort-Object -Unique |
    ForEach-Object { ($_ -split ' ')[0] } |
    Group-Object | Group-Object Count |
    Format-Table @{n='스레드수';e={$_.Name}}, @{n='파티수';e={$_.Count}}
```

1차 실험(`concurrency: 3`) 결과.

```
스레드수  파티수
3         47
2         51
1          2
```

100개 파티 중 98개가 **같은 행에 서로 다른 스레드에서 동시에 썼다.**

100이어야 한다. 이 숫자가 100인데 원장이 400이라는 것이
**"완료 판정은 한 번, 지급은 네 명" 이 정확히 일어났다**는 뜻이다.

## 7-1. 대조군 절차 — 같은 실험, 같은 통과, 다른 의미

`concurrency: 1` 로 되돌리고 그대로 다시 돌린다.
**통과했는데 아무것도 증명하지 않은 상태**가 어떤 모양인지 보여주는 대조군이다.
"그 실험이 정말 동시였나요" 라는 질문에 대한 답이 된다.

### 시작 전에 — 틀리기 쉬운 것 셋

**하나. 로그 파일 이름을 바꾼다.**
`boot.log` 를 그대로 쓰면 1차 실험 로그가 덮어씌워진다. 비교할 대상이 사라진다.
대조군은 `boot-c1.log` 로 남긴다.

**둘. `02_events.txt` 를 반드시 다시 만든다.**
시드는 기준값의 측정 시각을 `now() - 1시간` 으로 넣는다.
1차 때 만든 이벤트 파일의 `measuredAt` 은 그보다 **앞서게 되므로**,
워터마크에 걸려 400건이 전부 `Ignored[STALE_SNAPSHOT]` 으로 튕긴다.
완료 0건이 나오고 대조군이 성립하지 않는다.

**셋. DB 를 먼저 비운다.**
퀘스트가 이미 `COMPLETED` 라서, 안 지우면 완료 선점 UPDATE 가 0행을 받고
역시 아무 일도 일어나지 않는다.

`application.yml` 의 `concurrency` 를 **3 으로 되돌린다.**

### 판정표

| 항목 | 1차 (concurrency 3) | 대조군 (concurrency 1) | 뜻 |
|---|---|---|---|
| 완료 건수 | 100 | **100** | 같아야 한다 |
| XP 원장 | 400 / 12000 | **400 / 12000** | 같아야 한다 |
| 정합성 위반 | 0행 | **0행** | 같아야 한다 |
| 완료 로그 | 100줄 | **100줄** | 같아야 한다 |
| **스레드 수** | **3개** | **1개** | **여기만 달라야 한다** |
| 파티별 스레드 분산 | 2~3개가 98파티 | **전부 1개** | **여기만 달라야 한다** |

위 다섯 줄이 같고 아래 두 줄만 다를 때, 1차 실험의 정합성이
**우연이 아니라 동시성을 견딘 결과**라는 것이 확정된다.

만약 대조군에서 **완료가 100보다 적게 나오면** 대조군 준비가 잘못된 것이다.
6번(이벤트 파일 재생성)이나 2번(DB 비우기)을 건너뛰지 않았는지 본다.

> 더 극적인 대조군을 만들려면 `PartyQuestProgressService` 에서
> `claimCompletion` 의 반환값 확인을 없애고 돌리면 된다. 원장이 1600건이 된다.
> **반드시 되돌려야 한다.** 이 실험은 그 한 줄을 지키기 위한 것이다.

## 8. 말할 수 있게 되는 문장

> 파티 목표 4000보를 네 명이 동시에 채우는 상황을 파티 100개, 이벤트 400건으로 만들었습니다.
> 완료는 정확히 100번 일어났고 XP 원장은 정확히 400건이었습니다.
>
> 완료 판정을 `UPDATE ... WHERE status='ACTIVE' AND current_val >= target` 한 문장으로 선점하게
> 해서, 동시에 들어온 네 트랜잭션 중 하나만 1행을 받고 나머지는 0행을 받아 아무것도 하지 않습니다.
> 상태를 읽어서 애플리케이션에서 판단했다면 네 명이 전부 통과해 XP 가 네 배로 나갑니다.
>
> 반대 방향의 실패도 있었습니다. 멤버 기여분을 그때그때 합산하는 방식이면
> 커밋 전인 다른 멤버의 기여가 보이지 않아 아무도 목표 도달을 못 봅니다.
> 그래서 합계를 공유 카운터로 들고, 증분 UPDATE 한 문장으로만 올립니다.
>
> 그리고 이 실험이 진짜 동시였는지도 같이 확인했습니다.
> 컨슈머 스레드 수가 기본값 1이면 전부 직렬로 처리돼서, 통과하지만 증명하는 것이 없습니다.
